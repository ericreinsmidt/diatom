# Spike result - the blit, and why the hardware scaler was not needed

- **Date:** 2026-08-25
- **Question:** *`present` costs 8.4 ms against 1.65-4.2 ms for emulating the
  machine. Can the disp2 hardware scaler take that away?*
- **Status:** Answered, and redirected. **The scaler is not needed.** A row cache
  made the CPU blit **2.1-2.3x faster** with no new kernel interfaces.
- **Instrument:** [`tools/blitprobe.c`](../../tools/blitprobe.c)

## The plan, and why it stalled

The [warm-launch spike](2026-08-25-warm-launch.md) showed Diatom's own pixel
loop costs two to five times more than emulating the machine, which promoted
ADR-0013's disp2 hardware scaler from escape hatch to leading performance item.

Reconnaissance found the mechanism is real: the engine's layer carries a `crop`
rectangle and a `frame` rectangle, and scales between them. Our page flip is
already a crop change - `crop = (0, yoffset, 1024, 768)`. But fbdev can move the
crop and cannot resize it, and the driver advertises exactly one mode
(`U:1024x768p-60`), so scaling needs `/dev/disp` ioctls.

**Those need struct definitions this kernel does not publish.** `trimui/kernel_brick`
is a 404 and `trimui/firmware_brick` contains only a README, so there is no
authoritative `sunxi_display2.h` for firmware 1.1.1. Driving an undocumented
ioctl with structs guessed from another BSP, on a device where a mistake wedges
the display in-kernel, was a poor trade for headroom nothing was short of.

## The measurement that redirected the work

Before accepting that, one question was worth asking: **is the blit slow because
of the pixels it computes, or the memory it writes?** Framebuffer memory is often
uncached or write-combining, and if the write were the bottleneck then hardware
scaling would be the only real fix.

Same loop, same pixel count, two destinations:

```
256x224 -> 1024x768, 3.00 MB per frame, best of 20
  -> framebuffer (mmap /dev/fb0)    7.52 ms      418 MB/s
  -> ordinary heap (malloc)         7.53 ms      418 MB/s
```

**Identical.** Framebuffer memory is not slow, 418 MB/s is nowhere near this
SoC's memory bandwidth, and the cost is the loop itself - about 15 cycles per
pixel.

Which exposed the actual defect: **every source pixel was converted once per
destination pixel that sampled it.** At 4x horizontal and 3.4x vertical that is
roughly thirteen redundant RGB565-to-ARGB conversions of the same pixel.

## The fix

Convert each source row once into a scratch buffer, then expand from it. Two
slots, because a blended row needs the rows above and below; rows are looked up
by index, so consecutive destination rows sampling the same source row convert
nothing.

The nearest path - the default, and every pixel at a whole factor - becomes a
pure indexed copy with no arithmetic at all.

### A methodology note worth more than the result

The first comparison used numbers taken earlier in the day and appeared to show
only NES improving. Re-measured in one session, NES read **8.45 ms then and
6.44 ms now for identical code.** The device's clock behavior drifts between
sessions by enough to swamp a 20% effect. **A/B in one session or do not
compare.**

## Correctness, which mattered more than the speed

Eight combinations across four cores, six display modes and both filters, old
against new: **byte-identical captures throughout.**

Getting there required fixing the instrument first. The initial comparison
showed two cases differing in a 24-row band, and only at some frame counts -
the signature of a blinking sprite captured one frame apart, not a blit defect.
`diatom_port_capture` read the front page without waiting for the pending flip,
so **which frame you captured depended on how fast the blit was.** It now waits
for the mailbox to drain. A capture that is not deterministic cannot verify
anything, and it had been quietly non-deterministic since the flip thread was
written.

A first attempt at the corrected comparison also **passed falsely**: an argument
mismatch meant no captures were produced, both md5 sums were empty, and empty
compared equal. The test now refuses to report a result when a capture is
missing.

## Consequences

- **The disp2 hardware scaler is not needed** and its risk is not worth taking.
  It remains available if a future device or a much larger panel changes the
  arithmetic.
- **Sharp filtering became affordable.** It was 10.4-15.0 ms, which left no
  headroom; the same modes now cost far less, so the ADR-0014 decision to ship
  sharp but not default it could be revisited on looks alone rather than cost.
- **Captures are deterministic**, which every future visual comparison depends on.
