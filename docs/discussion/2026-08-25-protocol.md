# 2026-08-25 - the launcher protocol, first working version

Implementing [ADR-0009](../decisions/0009-launcher-protocol.md). The design was
already decided; this is execution, plus the measurement that justifies it.

## Why now

The [warm-launch spike](../spikes/2026-08-25-warm-launch.md) settled the order of
work. Two accepted ADRs - 0006 (cores stay resident) and 0008 (long-lived
process) - are justified by launches being fast in the steady state, and the
protocol is the thing that produces the steady state. Core options can wait;
without the protocol they have no delivery mechanism anyway.

The one thing that could have forced a redesign, display handoff between an
fbdev presenter and an EGL launcher, was retired by
[its own spike](../spikes/2026-08-24-display-handoff.md) the day before.

## What was built

- **`src/proto.c`** - one Unix socket, line-based, tab-separated `key=value`.
  Non-blocking, one connection at a time, unknown verbs and keys ignored for
  forward compatibility.
- **A resident core registry** in `core.c`. `diatom_core_resident(path)` opens a
  core once and returns the same one forever, so the second RUN naming it skips
  `dlopen` and `retro_init` entirely. Bounded at 8 deliberately: the 15.0 MB
  residency measurement was taken with six, and an unbounded registry would turn
  a measured decision into an unmeasured one.
- **`run_session()`**, extracted from `main`, so one process can run many games.
- **`tools/protodrive.c`**, a stand-in launcher, because the device has no
  Python and the protocol needed a client before PlayOS has one.

## Measured, on device

Five games across two cores, each run for three seconds then stopped:

```
<- READY  proto=1  state=idle
  RUN -> RUNNING     16.9 ms   Final Fantasy (USA).nes     first NES launch
  RUN -> RUNNING      6.3 ms   Dragon Warrior (USA).nes    core resident
  RUN -> RUNNING     24.0 ms   Parodius (Europe).sfc       first SNES launch
  RUN -> RUNNING      6.2 ms   Probotector (Europe).nes
  RUN -> RUNNING     17.2 ms   Star Fox (USA) (Rev 2).sfc  SNES resident
```

**6.2 ms for a resident NES game, against 625-750 ms for a cold spawn. About
100x.** The first launch of each core costs 7-10 ms more, which is that core's
`dlopen` being paid once and never again - the registry working, visible in the
numbers rather than asserted.

**Two numbers, and they mean different things.** `RUNNING` at 6.3 ms is the
*display handover* - when the launcher must stop drawing. The player sees a
frame after the ~30 ms warmup, so perceived launch is ~36 ms. Reporting the
handover as the launch time would flatter it.

## The contract that governs it

> `ERROR` means the game never started. `EXIT` means it ran and stopped.

`RUNNING` is sent after everything that can fail has failed, and **before the
warmup**, because the warmup already puts frames on the panel. A missing BIOS
reported as RUNNING-then-EXIT would make the launcher relinquish the screen for
a game that never existed, and the player would see a black frame before the
shelf returned.

`HANGUP` - the launcher dying - is deliberately **not** a stop. ADR-0008 exists
so that a launcher crash cannot take a running game with it.

## Still to do

- `STOP` is handled but `SAVED` and `PREVIEW` are not emitted.
- Manual save slots (ADR-0016) need the launcher menu, which needs the display
  handover this now provides.
- Display mode is not yet carried per RUN; it stays at whatever the process
  started with.
- `EXIT reason=` is always `user`. `crash` needs a way to distinguish a core
  that died from one that was stopped.
