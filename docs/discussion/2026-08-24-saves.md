# 2026-08-24 - saves and save states

Design in [ADR-0016](../decisions/0016-saves-and-save-states.md); this is what
was built and what it was checked against. All measurements on the device,
firmware 1.1.1.

## What the discussion nearly missed

The first pass answered "how do we get bytes to disk safely" and called it
saves. That is the mechanism, not the feature. The questions that actually
shape it - how many slots, does exit auto-save, which slot does it write to,
does launch auto-load, how do you quit without saving - were not asked until
Eric asked them. Recorded because the failure mode is subtle: the measurements
were real and the reasoning was sound, and it was still answering the wrong
question.

Two of those questions turned out to settle themselves:

- **The auto-save must not share a slot with the manual ones.** Not taste: if
  exit wrote to a numbered slot it would destroy a save the user made
  deliberately, which is a data-loss bug.
- **"Quit without saving" dissolves once the slots are separate.** Exiting
  always writes the resume slot harmlessly, so the real choice - resume, start
  fresh, load slot 3 - moves to launch time, where the player knows what they
  want, instead of a modal on the way out.

## Built and verified

**SRAM**, automatic. Read after `retro_load_game`, `memcmp` against a shadow
copy every frame, and when it differs and a second has passed, handed to a
writer thread. Verified: Final Fantasy wrote a `.srm` of exactly 8192 bytes
during play with no exit-path logging at all, which is the thread doing its job
and the exit flush correctly finding nothing left to do.

**Save states**, opt-in, taking paths rather than slot numbers. 21988-byte
payload plus a 112-byte header, round-tripped and restored.

**The signal path.** `kill -TERM` mid-play produced `terminated by signal;
saving` and both files on disk. That is the power-button case working: SIGTERM
arrives about 810 ms before death, an 8 KB flush costs 8 ms.

**The header check.** A state written by FCEUmm, offered to PicoDrive:

```
[warn] state: ff.state.auto was written by FCEUmm (SVN) 3a84a6f,
       this is PicoDrive 2.01-b0be121
diatom: no usable state at ...; starting the game normally
```

Refused, with the fallback that makes resume-by-default safe across a core
update: a bad state is not an error, it just means the game starts normally.

## What is not built

Manual slots and the in-game menu. Those need the launcher to take the display
on MENU, which needs the ADR-0009 protocol **and** a display handoff that has
not been proven for our case. ADR-0013 chose raw fbdev over the mali EGL path
for the frame rate; PlayOS draws through EGL; an fbdev presenter handing off to
an EGL presenter is the exact combination that wedged the PowerVR firmware
in-kernel this morning. PlayOS and minarch hand off successfully today, but
both are EGL, so their success says nothing about ours.

**Spike that before designing the menu.**

The useful consequence of the split: the data-loss defect is fixed now, with
nothing but command-line flags, while the slot feature waits behind the
hardest open item in the project.
