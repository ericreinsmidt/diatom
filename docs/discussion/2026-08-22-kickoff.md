# 2026-08-22 — Kickoff

First session. How the idea arose, what was established, what's still open.

## How we got here

Not from wanting to write a frontend. It came out of trying to build PlayOS on
a second machine while travelling, which surfaced how much friction minarch's
GPL lineage costs:

- `minarch/overrides/` holds nine patched GPL-3.0 files.
- `minarch/build.sh` needs a NextUI checkout at `$HOME/Projects/NextUI/workspace`.
- That checkout on the mini is at `v6.11.2-10-g96eeacd9`, on a WIP branch — the
  docs claim the baseline is `v6.11.2`. **Documented and actual baseline have
  diverged.**
- `libretro-common` and `libchdr` are gitignored in NextUI and cloned
  **unpinned** by `workspace/all/minarch/makefile:121`, so a fresh build can
  pick up a different libretro-common than the mini used.
- PlayOS's own docs say "eight files" in two places; there are **nine**.
  `ma_options.c` is absent from the table — a small GPL §6 completeness gap.

None of that is a bad decision. It's what happens when a project depends on
someone else's copyleft code and the details stop being written down.

## Established this session

- The frontend is what we'd build; **not** starting from MinUI's minarch, which
  would inherit the same GPL obligations and an older codebase while delivering
  none of the independence sought. → ADR-0002 context.
- Separate repository. → **ADR-0002 (Proposed)**
- ADRs adopted as the decision-recording practice. → **ADR-0001 (Proposed)**
- Register created with 15 sections, tagged `[LB]` / `[OPEN]` / `[LATER]`.

## Key insights worth not losing

**The core list isn't the frontend's business.** PlayOS's `systems.cfg` already
maps system → core → ROM folder → tag → art → accent. The frontend needs only
"core path, ROM path, tag". So curation lives in each firmware's config, and the
frontend stays generic. This dissolves the apparent tension between "systems I
personally like" and "reusable base for other handhelds" — they were never in
conflict. "Which systems" is really a question about the **test matrix** and the
**RAM budget**, not about frontend features.

**Residency doesn't scale the way the current design assumes.** PlayOS holds
three lightweight 2D cores resident, 1100ms → 200ms. On 1GB, adding heavier
cores (fbneo, pcsx_rearmed) breaks keep-everything-resident. Expanding the
system list therefore forces a residency *policy* — keep-one, LRU, or tiered —
that PlayOS never needed. This is the most interesting design problem in the
project.

**The Brick's 1024×768 is a gift.** Integer scaling works for essentially every
2D system: NES 3× → 768×720, SNES 3× → 768×672, Genesis 3× → 960×672, Neo Geo
3× → 912×672, PS1 3× → 960×720, GBA 4× → 960×640, GB 5× → 800×720. All fit. One
scaling path, no filtering, no fractional math. **Open question:** is
integer-only a principle to enforce everywhere, or a Brick luxury? Other panels
(640×480, 720×720, 1280×720) may break it.

**PlayOS's three systems are curatorial, not technical.** From `systems.cfg`:
"In release order: NES '85, TurboGrafx-16 '89, Game Boy Advance '01." One
console per era, deliberately. Expanding the list is a taste decision, not a
capability one.

**"Abstracted to perfection" needs a definition or it becomes a liability.**
Agreed formulation: seams in the right places, nothing leaking across them —
*not* maximum layers. On 1GB at 60fps, indirection costs real cycles. Register
§0 records the test: a boundary needs two real implementations to earn itself.
Desktop + device is the bar.

**Process is subject to the same test.** Ceremony that doesn't earn its keep
gets cut. ADR-0001 records abandonment as the real risk, with a trigger for
cutting the format down rather than silently dropping it.

## Corrections logged

Two assertions made and then disproved by checking. Both are why CLAUDE.md
rule 4 exists.

1. Claimed the tg5040 toolchain would need x86_64 emulation on Apple Silicon.
   `docker manifest inspect` showed the image is multi-arch; it pulls arm64 and
   builds natively. Eric challenged this correctly on the grounds that the
   target device is ARM.
2. Proposed Tailscale SSH as a fallback for reaching the mini. Tailscale SSH's
   *server* side is Linux-only; `tailscale up --ssh` on macOS is a no-op. Should
   have been checked before being suggested.
